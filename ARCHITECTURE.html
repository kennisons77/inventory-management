Factory Inventory Management System

Full-stack Architecture & System Design

System Overview

A full-stack demo application for managing factory inventory, tracking orders, forecasting demand, and planning restocking operations. The system uses in-memory mock data (no database) with a modern Vue 3 frontend and Python FastAPI backend.

Key Feature: Budget-driven restocking recommendations based on demand forecasts, with orders appearing in the unified Orders tab.

Frontend Vue 3 + Composition API Vite (fast builds) axios for HTTP

API Endpoints

Inventory

GET /api/inventory — Filters: warehouse, category
GET /api/inventory/{id} — Get single item

Orders

GET /api/orders — Filters: warehouse, category, status, month (includes Restocking orders)
GET /api/orders/{id} — Get single order

Demand & Forecasting

GET /api/demand — All demand forecasts (no filters)
GET /api/backlog — Backlog items with purchase order status

Restocking (New)

GET /api/restocking/recommendations — Demand forecasts sorted by demand gap (highest first), with computed demand_gap and restock_cost
POST /api/restocking/orders — Create restocking order (generates order_number RST-YYYY-NNNN, sets expected_delivery to now + 14 days)
GET /api/restocking/orders — List all restocking orders

Dashboard & Analytics

GET /api/dashboard/summary — KPI totals (inventory value, low-stock count, pending orders)
GET /api/spending/* — Spending summary, monthly, categories, transactions
GET /api/reports/* — Quarterly stats, monthly trends

Filtering Strategy

Standard Pattern: Filter parameters are optional query strings. Value 'all' or missing = no filter applied. Backend applies filters sequentially: warehouse → category → status → month.

Filter System

All views share four filter dimensions via the useFilters() singleton composable:

Time Period

Supports months (2025-01) and quarters (Q1-2025). Drives `order_date` filtering in Orders and Dashboard.

Warehouse

San Francisco, London, Tokyo. Filters inventory, orders, and summary stats.

Category

Circuit Boards, Sensors, Actuators, Controllers, Power Supplies. Applies across inventory and orders.

Order Status

Delivered, Shipped, Processing, Backordered, Restocking. Filters Orders tab only.

Design Note: Filters are applied via query params. FilterBar binds to shared refs; all views watch these refs and reload via API calls automatically.

Performance & Scalability Notes

In-Memory Data

Pros: Fast reads, no network latency to DB. Cons: Data resets on server restart, no persistence.

Current Scale

~100 orders, ~30 inventory items, 9 demand forecasts. Suitable for demo; filtering is O(n) list comprehensions.

Scaling Path

Add PostgreSQL + ORM (SQLAlchemy), pagination, database indexes, Redis caching, async queries.

Security & Deployment

Development Only: This is a demo application. CORS allows all origins, no authentication, no rate limiting. Not suitable for production without security hardening.

For Production:

  • Add user authentication (OAuth2, JWT tokens)
  • Restrict CORS to specific origins
  • Validate and sanitize all inputs
  • Use HTTPS only
  • Implement rate limiting and API quotas
  • Add database for persistence
  • Move secrets to environment variables
  • Set up proper logging and monitoring

Recent Features

Restocking Feature (Latest)

Budget-Driven Restock Recommendations:

  • Budget slider: Set available budget ($0–$500k)
  • Recommendations: Demand forecasts sorted by demand gap (forecasted − current)
  • Smart Selection: Greedy algorithm fills budget with highest-gap items first
  • Order Placement: Creates restocking order with 14-day delivery lead time
  • Unified View: Restocking orders appear in Orders tab with purple badge
  • Persistence: In-memory storage; survives page refresh, resets on server restart
